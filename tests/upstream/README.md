# The own tests of the ported rules

Every rule veslint ports carries the test cases of its own upstream test, besides its fixtures in
`tests/rules/<rule>/`. For the 105 rules of typescript-eslint they are the cases of
`packages/eslint-plugin/tests/rules/<rule>.test.ts` (and of the test files under
`packages/eslint-plugin/tests/rules/<rule>/`) at v8.72.2: 26,825 cases, 2 of which upstream skips
through `dependencyConstraints`.

- `tests/rules/<rule>/upstream.json`: the cases of the rule, one per line, as RuleTester receives
  them (code, options, file name, how the parser gets the types, the errors and the output the test
  expects), and the rule's `meta.messages`. Generated by `tools/gen_upstream_cases.mjs`.
- `fixtures/`: a copy of `packages/eslint-plugin/tests/fixtures`, the directory the tests lint in:
  the case is the text of its file (`file.ts`, `react.tsx`, `unstrict/file.ts`), and the other files
  and the `tsconfig*.json` are those of upstream.
- `known.txt`: the cases that do not give what their test expects, and why.
- `typescript-eslint.LICENSE`: the license of the tests and fixtures (MIT).

## How they run

- **veslint** (`tests/run.sh`, part of `make test`): `tests/upstream_check.py` sends every case to
  one `veslint --server`, with the code of the case as the unsaved text of its file, and checks what
  the test expects as RuleTester checks it: no problem for a valid case; for an invalid one, the
  number of problems, their messageId, the message (as written, or built from the data and
  `meta.messages`), the line, the column, the endLine and endColumn when the test gives them, and
  the suggestions (messageId, description and the text each one leaves), and the output of the
  fixes, pass after pass, applied as ESLint's SourceCodeFixer applies them. It takes about 2
  minutes on one core.
- **ESLint** (`tests/rules/reference.sh`): `tests/rules/upstream_eslint.mjs` runs ESLint 10.15.0 with
  typescript-eslint 8.72.2 the way RuleTester does (ecmaVersion "latest", sourceType "module",
  unused disable directives reported, the parser's caches cleared between test files) and checks
  the same expectations: it shows that the fixtures reproduce typescript-eslint's own run. Then
  veslint's output on each case must be ESLint's, line for line and in the same order, with the
  fixes and the suggestions.

Upstream, each test file runs in a process of its own, and the program of the fixtures keeps the
last text each file had: both scripts start every test file from the files on disk, and keep the
texts within it.

## Regenerating the cases

`upstream.json` changes only when the pinned typescript-eslint changes:

```sh
git clone --depth 1 --branch v8.72.2 --filter=blob:none --sparse \
  https://github.com/typescript-eslint/typescript-eslint build/upstream/typescript-eslint
cd build/upstream/typescript-eslint
git sparse-checkout set packages/eslint-plugin/src packages/eslint-plugin/tests \
  packages/eslint-plugin/typings packages/rule-tester/src /package.json /pnpm-workspace.yaml /pnpm-lock.yaml /LICENSE
cd ../../..
bun tools/gen_upstream_cases.mjs            # every rule of tests/rules, or name some
```

The test files are loaded as the test runner loads them, with the stubs of `tools/upstream/` in the
place of `@typescript-eslint/rule-tester` (its `run` records the cases) and of `vitest`, and the
other packages from `build/eval` (typescript-eslint 8.72.2, TypeScript 6.0.3).

## eslint-plugin-vue (the `vue/*` rules)

The cases of `tests/lib/rules/<rule>.test.ts` (and `tests/lib/rules/<rule>/*.test.ts`, the test file
of each feature of no-unsupported-features) of vuejs/eslint-plugin-vue v10.12.1 (`d33df42`), for
all its 256 rules, in `tests/rules/vue/<rule>/upstream.json`: 10,899 cases and 31 lints. The tests run with vitest and ESLint 10's own RuleTester, which `tests/eslint-compat.ts`
hands them (eslint-compat-utils); `tools/upstream/vue-test.mjs` stands in for that module while
`tools/gen_upstream_cases.mjs` loads them: `RuleTester.run` records the cases, and `ESLint` and
`Linter` are the real classes, which record what the `it` blocks of comment-directive, block-order
and no-unused-properties lint (run for real, with ESLint): those are the `lints` of upstream.json,

A case is written as ESLint 10's RuleTester runs it: the tester's configuration under the case's
(languageOptions, parserOptions and settings merged), with

- `parser`: the parser by package name (`vue-eslint-parser`, `@typescript-eslint/parser`, `espree`
  when the test gives none, ESLint's default), and `parserOptions.parser`, the script parser of
  vue-eslint-parser, by name too (one, `{"ts": …}` by lang, or null); upstream gives the module or
  its resolved path, which vue-eslint-parser requires: the same module;
- `filename` as the test gives it, relative to the directory the tests run in (the clone's root);
  a path the test builds in it (`path.join(process.cwd(), 'test.vue')`, an option's module) is
  written `<cwd>/…`. No `filename`: ESLint lints `<input>`;
- the typed cases (`tests/test-utils/typescript.ts`): `file` `src/test.vue` of
  `tests/upstream/vue/fixtures` (a copy of the clone's `tests/fixtures/typescript`) with the program
  of `tsconfig` (`via: "project"`, `parserOptions.project` upstream) and `extraFileExtensions`;
- `sfc`: whether vue-eslint-parser reads it as a Vue file (its isVueFile: a `.vue` file, or a text
  that starts with `<`; with espree or typescript-eslint's parser a `test.vue` is a script), and
  `script`: the lang of the script vue-eslint-parser parses (`js` without a lang attribute, `none`
  without a script), or for another file `ts`/`tsx` by its extension or by typescript-eslint's
  parser, else `js`/`jsx`; `scripts` when the two scripts of a file differ. veslint lints only
  TypeScript scripts in a `.vue` (`.claude/VUE.md`): the cases with a JavaScript script, and those
  that are not a `.vue`, stay here, to be listed as not applicable;
- `rule` for the cases of another rule (jsx-uses-vars runs ESLint's no-unused-vars with
  `vue/jsx-uses-vars` on), and `plugins` (`{"vue": {"rules": [...]}}`) for the rules of
  eslint-plugin-vue a case turns on itself;
- `messages`: those of the published rule, which the generator checks are the source's.

The rules that wrap a rule of ESLint Stylistic take it from the `@stylistic/eslint-plugin` they find
from the current directory when the plugin loads (5.10.0, in the clone's node_modules), and ESLint

root, the typed ones in the directory `tests/upstream/vue/setup.sh` makes), and lints the `lints`
again: all of them give what their test expects (`tests/upstream/vue/known.txt` would list those
that do not). `--out DIR` writes ESLint's problems for each case. It takes about 30 seconds.

They need the clone with the published build as its `dist` (the tests import it, and a case of

### How veslint runs them: TypeScript only

veslint lints only TypeScript (`.claude/VUE.md`), and reads every `.vue` file with vue-eslint-parser
and typescript-eslint's parser (also its template expressions, which upstream parses with espree).
`node tests/rules/vue/upstream_ts.mjs [vue/<rule>...]` (without names, the vue/* rules veslint has:
the directories of `tests/rules/vue` with an `expected.txt`) converts the cases of each rule that way
and writes them to `tests/rules/vue/<rule>/upstream.ts.json`, which `tests/upstream_check.py` runs
for a `vue/` rule:

- a `.vue` case gets `lang="ts"` on each top-level `<script>` without a lang (`lang="js"` becomes
  `ts`, `jsx` `tsx`; vue-eslint-parser finds the elements) and typescript-eslint's parser as
  vue-eslint-parser's `parserOptions.parser`; a case that is not a `.vue` becomes a TypeScript file
  (`test.ts`, `.tsx` with JSX) read by typescript-eslint's parser; a case without a file name is
  `test.vue` (or `test.ts`);
- ESLint's RuleTester runs the converted case: if it still gives what the test expects, the
  expectation stays the test's (`"expectation": "upstream"`); if not, it is what ESLint gives on the
  converted case (`"expectation": "eslint"`: every problem with its messageId, message, location,
  end and suggestions, and the output of one pass of fixes);
- a `.vue` file ESLint reads as a script (espree or typescript-eslint's parser without
  vue-eslint-parser: 2,984 cases of 26 script rules, the cases of `Vue.component(…)`,
  `export default {…}` and the like of the script rules) stays a `.vue` file of the same name, as
  veslint reads every `.vue` file, an SFC: its text becomes the content of a
  `<script lang="ts">…</script>` (and so does the text of its expected output and of the outputs of
  its suggestions). The rules see the same script, in a file of the same name (`isVueFile`), and
  the cases' texts start with a line break, so the positions stay but on the first line; the
  expectation is still the test's when ESLint gives it on the wrapped case (all but those whose
  problems are on the first line, which take ESLint's);
- a case of another rule (`rule`: jsx-uses-vars' tests run ESLint core's `no-unused-vars`, with
  `vue/jsx-uses-vars` turned on by a comment of the case) runs that rule, typescript-eslint's
  `no-unused-vars` for ESLint core's, as the lints do (`tests/upstream_check.py` turns on the
  case's `rule` instead of the tested one);
- `skipped` lists the cases that cannot be converted, with why: a text with a lone surrogate (a file
  cannot hold it), a `.vue` file read as a script whose text has a `</script`, a script whose lang
  is not JavaScript or TypeScript, or a converted text typescript-eslint's parser rejects;
- the `lints` of comment-directive (`ESLint` with the `vue/vue` processor) are converted the same
  way, with the rules of their configuration that veslint has (`no-unused-vars` becomes
  `@typescript-eslint/no-unused-vars`), and their expectation is all that ESLint gives on the
  converted text, compared whole and in order.

`tests/upstream_check.py` runs them in the fixtures `tests/upstream/vue/setup.sh` makes (a case's
file at its path there; the typed ones `src/test.vue` with the program of `tsconfig.json`), with
one pass of fixes (ESLint's RuleTester). A case that is not typed has no program in ESLint, which
the rules that read the types only when the parser has one see (isExhaustiveSwitch, the props of a
type the checker gives): veslint gets `projectService: false` for it. `tests/rules/reference.sh` checks with ESLint that
`upstream.json` gives what each test expects, that `upstream.ts.json` is what
`upstream_ts.mjs --check` makes now, and that veslint prints, case by case, ESLint's lines on every
converted case (`--out DIR` writes them).


## eslint-plugin-svelte (the `svelte/*` rules)

The cases of `tests/src/rules/<rule>.ts` of the package `packages/eslint-plugin-svelte` of
sveltejs/eslint-plugin-svelte at `eslint-plugin-svelte@3.24.1`, for all its 86 rules, in
`tests/rules/svelte/<rule>/upstream.json` (`@typescript-eslint/no-unnecessary-condition` a level
deeper): 1,478 cases, 64 more its fixtures' requirements leave out, and 29 lints. The tests run
with mocha and ESLint's RuleTester (`tests/utils/eslint-compat.ts`, which
`tools/upstream/svelte-test.mjs` stands in for while `tools/gen_upstream_cases.mjs` loads them).
All but two test files hand RuleTester what `loadTestCases` of `tests/utils/utils.ts` reads from
the rule's fixtures, `tests/fixtures/rules/<rule>/{valid,invalid}/`: each `*input.<ext>` (or
`+<route>` file) is a case, with the options and configuration of `<case>-config.json` or the
directory's `_config.json` (`.cjs`), the problems of `<case>-errors.yaml` (message, line, column,
suggestions: no end) and, for a fixable rule, the output of `<case>-output.<ext>` (null when it is
the input). The generator loads `utils.ts` itself, listing the directories sorted (as node does),
recording the fixtures whose `<case>-requirements.json` / `_requirements.json` do not hold with the
packages installed (`skip`: Svelte 3/4-only fixtures, 4 ESLint 9-only ones, 3 for
typescript-eslint < 6.11), and failing where upstream would write a missing errors.yaml or output.
no-conflicting-module-names lists its cases (files of its fixtures that it reads the siblings of),
and comment-directive lints with ESLint in `it` blocks: those are the `lints`, run for real.

A case is written as ESLint 10's RuleTester runs it: the tester's configuration under the case's,
with

- `file`: the case's own file, relative to `tests/fixtures/rules`; every case lints its fixture in
  place (some rules read the disk around it: svelte.config.js, the modules beside a component), in
  the package's directory, the tests' current directory (the routes of SvelteKit in the
  configurations are relative to it, and the plugin loads typescript, sass, less and stylus from
  it);
- `tsconfig`/`via: "project"`: `loadTestCases` gives every case `parserOptions.project`,
  `tests/fixtures/rules/tsconfig.json` (`include: ["**/*.svelte", "**/*.ts"]`), and
  `extraFileExtensions: [".svelte"]`: a script typescript-eslint's parser reads has the types of
  that program (`typescript: true`; 330 cases), one program for all (mocha runs every test file in
  one process);
- `parser`: svelte-eslint-parser (for `.svelte` and `.svelte.{js,ts}` files),
  `@typescript-eslint/parser` (a `.ts` file), `espree` (a `.js` file: ESLint's default), and
  `parserOptions.parser` by name as upstream gives it, `{"ts": "@typescript-eslint/parser", "js":
  "espree"}`, which svelte-eslint-parser requires from its own directory and indexes with the
  script's `lang` (`lang="typescript"` gets espree);
- `languageOptions`: ecmaVersion `latest`, sourceType `module`; the browser globals of `globals`
  16.4.0, which every case of `loadTestCases` has, are the `languageOptions` of the upstream.json,
  under each case's;
- `configModule`: the `_config.cjs` of a configuration with functions (svelteConfig's `onwarn`,
  `warningFilter`, `compilerOptions.runes`), each written `{"$function": <source>}`;
- `svelte`: whether svelte-eslint-parser reads the file as a component (any file but
  `.svelte.js`/`.svelte.ts`, which it parses as a script module), and `script`: the lang of the
  component's one script program (the `lang` of its `<script>` elements, the last one's winning,
  as svelte-eslint-parser merges them; `js` without one, `none` without a script; `scripts` when
  the elements differ), or the extension of another file. 1,455 components (329 with a TypeScript
  script, 830 JavaScript, 19 another lang, 277 without a script) and 23 other files (12 `.js`, 1
  `.ts`, 10 script modules). The cases with a JavaScript script stay here (veslint lints only
  TypeScript scripts: `.claude/SVELTE.md`), to be converted to `lang="ts"` as for Vue;
- `messages`: those of the published rule, which the generator checks are the source's.

`node tests/rules/svelte/upstream_eslint.mjs [--out DIR] [svelte/<rule>...]` runs every case with
ESLint 10.15.0 and the published eslint-plugin-svelte through ESLint's own RuleTester (each case
alone, in place) and lints the `lints` again: all of them give what their test expects
(`tests/upstream/svelte/known.txt` would list those that do not), also with svelte 5.57.3. It
takes about 45 seconds and 1.5 GB.

They need the clone and the packages of the tests (svelte 5.56.0 and the rest as the monorepo's
lockfile has them; ESLint 10.15.0, typescript-eslint 8.72.2 and TypeScript 6.0.3 instead of
9.39.1, 8.57.0 and 5.9.3):

```sh
git clone --depth 1 --branch eslint-plugin-svelte@3.24.1 https://github.com/sveltejs/eslint-plugin-svelte build/upstream/svelte
mkdir -p build/upstream/svelte-deps && cd build/upstream/svelte-deps
# package.json: {"private": true, "dependencies": {"@typescript-eslint/parser": "8.72.2",
#   "eslint": "10.15.0", "eslint-plugin-svelte": "3.24.1", "globals": "16.4.0", "less": "4.4.2",
#   "postcss-nested": "7.0.2", "sass": "1.93.2", "semver": "7.7.3", "stylus": "0.64.0",
#   "svelte": "5.56.0", "svelte-eslint-parser": "1.10.1", "svelte-i18n": "4.0.1",
#   "typescript": "6.0.3", "yaml": "2.9.0"}}
npm install --ignore-scripts --no-audit --no-fund
cd ../../..
bun tools/gen_upstream_cases.mjs svelte/      # every rule; or name some: svelte/indent
```

The generator also makes the package's node_modules (links to `build/upstream/svelte-deps`),
which the reference script needs.

### How veslint runs them: TypeScript only

veslint lints only TypeScript scripts of `.svelte` files (`.claude/SVELTE.md`), and reads every
component with svelte-eslint-parser and typescript-eslint's parser as its one script parser (also its
template expressions, and a component without a script, which upstream parses with espree).
`node tests/rules/svelte/upstream_ts.mjs [--out DIR] [--check] [svelte/<rule>...]` (without names, the
svelte/* rules veslint has: the directories of `tests/rules/svelte` with an `expected.txt`) converts
the cases of each rule that way and writes them to `tests/rules/svelte/<rule>/upstream.ts.json`,
which `tests/upstream_check.py` runs for a `svelte/` rule:

- a component gets `lang="ts"` on each top-level `<script>` without a lang (`lang="js"` and
  `lang="javascript"` become `ts`; the Svelte compiler finds the elements), and
  `parserOptions.parser` becomes `@typescript-eslint/parser` (one parser, not one by lang); it keeps
  its file and the program of `tests/fixtures/rules/tsconfig.json`. A component the compiler rejects
  keeps its text (its error is the case) when its scripts are TypeScript already;
- a JavaScript file that is not a component becomes a TypeScript file (`x.js` -> `x.ts`,
  `x.svelte.js` -> `x.svelte.ts`), which is not on disk and so in no program (no types);
- RuleTester runs the converted case: if it still gives what the test expects, the expectation
  stays the test's (`"expectation": "upstream"`); if not, it is what ESLint gives on the converted
  case (`"expectation": "eslint"`: every problem with its messageId, message, location, end and
  suggestions, and the output of one pass of fixes). The inserted `lang="ts"` is an attribute of the
  script's start tag, which the rules about tags and attributes see: most of those cases take
  ESLint's expectation;
- `skipped` lists the cases that cannot be converted, with why: those upstream's requirements leave
  out (Svelte 3/4 and the like), a script whose lang is neither JavaScript nor TypeScript (`sass`), a
  configuration with functions (`_config.cjs`: a veslint configuration is JSON), a text with a lone
  surrogate, a case of no-conflicting-module-names whose subject is a JavaScript file's name, or a
  converted text the parser rejects;
- the `lints` of comment-directive (`ESLint` with the `svelte/svelte` processor) are converted the
  same way, with the rules of their configuration that veslint has (`no-unused-vars` becomes
  `@typescript-eslint/no-unused-vars`; `no-undef` and ESLint core's `space-infix-ops` are left out),
  and their expectation is all that ESLint gives on the converted text, compared whole and in order.

`tests/upstream_check.py` runs them in place, in the clone's `tests/fixtures/rules` (the typed ones
with the program of its `tsconfig.json`), from the package's directory (the routes of SvelteKit of
some configurations are relative to it), with one pass of fixes, and turns the rule on as a warning,
as ESLint's RuleTester does (the line of a report without a messageId says `warning`).
`tests/run.sh` runs them for the svelte/* rules veslint has ("eslint-plugin-svelte's own tests");
`tests/rules/reference.sh` checks with ESLint that `upstream.json` gives what each test expects,
that `upstream.ts.json` is what `upstream_ts.mjs --check` makes now, and that veslint prints, case by
case, ESLint's lines on every converted case. For the 34 rules of batch SR0: 316 cases and lints,
212 with their test's expectation, 73 with ESLint's on the converted case, 29 lints, 2 not
convertible (block-lang's `lang="sass"` and `lang="scss"` scripts).
